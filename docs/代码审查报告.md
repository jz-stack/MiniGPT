## 二、阻断问题（P0）

### B1. `splitText` 在 `overlap >= chunkSize` 时不终止，内存爆炸

**位置**：`backend/src/services/splitter.ts:17-23`

**原因（事实）**：循环步进为 `start = end - overlap`，其中 `end = start + chunkSize`，故实际前进量为 `chunkSize - overlap`。当 `overlap >= chunkSize` 时该值 `<= 0`，`start` 不再前进甚至转为负数，而 `while (start < clean.length)` 恒为真 → 死循环，每轮仍 `push` 一个 `slice()` 片段。

**实测证据**：
- 逐行复刻循环，`chunkSize=100 / overlap=500`：1 秒内迭代 3000 万次，`start` 一路负增长到 `-12000000400`，堆内存 446MB，不终止。
- 调用真实函数 `splitText('A'.repeat(3000), 100, 500)`（tsx 直接加载 `splitter.ts`）：**4218ms 后抛 `RangeError: Invalid array length`，堆峰值 ~2GB**。

**可达路径（事实）**：`SettingsView.vue:41-44` 对 `chunkSize` 与 `chunkOverlap` 独立设限（min/max 分别为 100/2000 与 0/500），**无交叉校验**；`documents.ts:49-50` 直接取用这两个值。因此用户在设置页填 `chunkSize=100`、`chunkOverlap=500` 属合法操作，之后上传任意文档即触发。由于 `documents.ts:35` 先 `res.json()` 再后台处理，HTTP 请求已返回 200，故障表现为进程内存耗尽。

**改法**：
1. `splitText` 入口钳制，保证步进恒为正：`const step = Math.max(1, chunkSize - Math.min(overlap, Math.max(0, chunkSize - 1)))`，循环改为 `start += step`；并校验 `chunkSize >= 1`、`overlap >= 0`。
2. `POST /api/config`（`config.ts:43-52`）与 `documents.ts:49-50` 使用处加交叉校验：`chunkOverlap < chunkSize`，否则 400 并回滚。

**验证方式**：表驱动单测 `[[100,500],[500,500],[100,100],[500,80],[1,0]]`，断言函数在 100ms 内返回、`chunks.length` 有界、`chunks[0].length <= chunkSize`；参考本报告的复现脚本（逐行复刻 + 真实函数两条路径）。

### B2. 流式增量写入裸对象，Vue 响应式失效 → 无打字机效果

**位置**：`frontend/src/stores/chat.ts:70-100`（核心 76、85-96 行）

**原因（事实）**：`const aiMsg: Message = {...}`（76 行）创建的是**裸对象**；`this.messages.push(aiMsg)`（77 行）经 Vue 的数组插桩方法存入的是原始对象而非 reactive 代理。随后回调中 `aiMsg.content += delta`（86 行）、`aiMsg.streaming = false`（89 行）、`aiMsg.sources = sources`（83 行）全部绕过 reactive 的 `set` trap，不触发 `trigger`。

**实测证据（真实 Pinia，非模拟）**：以 `createPinia/setActivePinia/defineStore` 复刻同构 action，用 `effect` 模拟组件渲染，输出渲染快照序列：

```
#0 (empty)
#1 (empty)
#2 user:"hi"
#3 assistant:""[光标]
#4 assistant:"你好，世界"
```

全程**无任何中间态**。即：生成期间气泡为空且光标长亮，答案在流结束时因 `this.streaming = false`（这次是代理写）触发整组件重渲染而**一次性整段出现**。

**影响**：`README.md:15` 声称的 "SSE 打字机效果" 实际不生效；同类问题也影响引用来源的即时显示。数据本身正确（最终 `content` 为 `"你好，世界"`），属纯渲染缺陷。

**改法**：先 push 占位、再通过代理引用回取，或直接把占位对象声明为 `reactive`：

```ts
const aiMsg: Message = { role: 'assistant', content: '', sources: [], streaming: true }
this.messages.push(aiMsg)
const msg = this.messages[this.messages.length - 1]   // 代理引用，后续只改 msg
```

回调内一律改用 `msg.content` / `msg.sources` / `msg.streaming`。`stopStreaming`（102-107 行）中 `last.streaming = false` 已是通过代理访问，无需改动。

**验证方式**：上述 Pinia 复现脚本（断言 `seen.length >= 3` 且出现中间长度快照）；或 E2E 在生成过程中断言气泡文本长度严格递增 ≥2 次。

### B3. 客户端断开不中止上游，且 user / assistant 落库不一致

**位置**：`backend/src/routes/chat.ts:44-122`（关键：64-66、106-114、118-121）；前端 `frontend/src/api/sse.ts:96`

**原因（事实）**：
1. 路由内**没有** `req.on('close', ...)`，`streamChat`（`llm.ts:31-54`）也未接收 `AbortSignal`。前端 `stopStreaming`（`stores/chat.ts:102-107`）只 abort 本地 fetch，服务端既不知道也不停止，仍继续消费 LLM 流并逐帧写入已断开的连接。
2. 用户消息在 64-66 行**先入库**，助手回复在 112-114 行**仅在流正常结束后**入库。二者非原子：中止或异常时留下"有 user、无 assistant"的消息对；`catch` 分支（118-121）只下发 SSE error，既不回滚 user 消息也不保存已生成的部分答案。
3. 会话历史在 88-92 行按 `ORDER BY id DESC LIMIT 20` 读取，会把上述残缺消息带回上下文。

**已排除的假设（避免误判）**：实测复刻该写入模式（express + SSE + 客户端 150ms 后 abort + 服务端继续 `res.write` 200 次），**进程未崩溃、未抛 `uncaughtException`/`unhandledRejection`**，属静默失败。因此问题定性为"资源浪费 + 数据不一致"，而非可用性故障。

**改法**：
1. 早退：`const ac = new AbortController(); req.on('close', () => ac.abort())`，并把 signal 透传给 OpenAI SDK（`client.chat.completions.create(params, { signal })`，`llm.ts:38-43`）。
2. 落库改为在 `finally` 中执行，保存已累积的 `answer`；若因中断而为空，写入明确标记（如 `content = ''` + 状态字段 `interrupted`），保证 user/assistant 成对。
3. 事务化：user 插入与 assistant 插入包在同一个事务中；或为 `messages` 增加 `status` 字段，检索历史时过滤未完成消息。

**验证方式**：生成中点击"停止"，断言该会话消息表为偶数条且成对；检查 LLM 服务侧 token 用量在断开后停止增长；并发脚本对同一 `conversationId` 连续发起后校验历史顺序一致。

### B4. 无鉴权 + CORS 全开 + `llmBaseUrl` 可写 → API Key 外泄

**位置**：`backend/src/index.ts:12`、`backend/src/routes/config.ts:43-52`、`backend/src/services/llm.ts:14-23`、`backend/src/services/embedding.ts:9-18`

**原因（事实）**：
1. `index.ts:12` 为 `app.use(cors())`，即默认配置。已核实依赖默认值（`backend/node_modules/cors/lib/index.js:9-12`）：`origin: '*'`、`methods: 'GET,HEAD,PUT,PATCH,POST,DELETE'`、`preflightContinue: false`、`optionsSuccessStatus: 204` → 任意 Origin 的预检都会被放行。
2. 全项目**无任何认证/授权中间件**（`index.ts:16-18` 直接挂载三个路由）。
3. `config.ts:43-52` 允许任意调用方写入 `llmBaseUrl` / `embeddingBaseUrl`，且**写入侧无任何来源校验**。
4. `llm.ts:15-17`、`embedding.ts:10-12` 的取值顺序是"**数据库设置优先于 `.env`**"，随后 `llm.ts:36` / `embedding.ts:29` 用该 baseUrl 构造 OpenAI 客户端，apiKey 会作为 `Authorization: Bearer` 发往该地址。

**攻击链（事实推导，实际被利用需服务处于运行状态——此处标注为风险场景而非已发生事件）**：
用户本机运行服务 → 用户浏览器打开任意恶意页面 → 该页 JS 对 `http://localhost:8000/api/config` 发预检 + `POST`（预检因 `origin:'*'` 通过）→ 写入 `llmBaseUrl = https://attacker.example/v1` → 用户之后每次提问，后端都把**真实 apiKey** 发到攻击者服务器。同一路径亦可指向内网地址构成 SSRF。

注意：`config.ts:33-34` 的 GET 掩码（`'••••••••'`）**不构成防护**——掩码只挡读，不挡写；攻击者无需读到明文即可完成改写。

**改法**：
1. `cors({ origin: ['http://localhost:3000'] })`；生产同源部署时直接移除 `cors()`。
2. 为 `/api/config` 的写操作（及所有写接口）加来源校验（校验 `Origin`/`Host` 属于本机白名单）+ 启动时生成的一次性本地令牌，前端经注入方式携带。
3. 对 `llmBaseUrl` / `embeddingBaseUrl` 做 allowlist（至少强制 `https:` + 域名白名单），或改为仅允许 `.env` 注入、不在运行时改写。
4. apiKey 不以明文落库（当前 `settings.value` 为明文 TEXT），或明确文档化"仅限本机使用"并默认只监听 `127.0.0.1`（`index.ts:30` 当前监听全部网卡）。

**验证方式**：从 `http://evil.test` Origin 发起预检，断言返回不含 `Access-Control-Allow-Origin: *`；直接 `POST /api/config` 改写 baseUrl，断言被 401/403 拒绝；`netstat` 确认监听地址为 `127.0.0.1` 而非 `0.0.0.0`。

## 三、重要问题（P1）

### M1. 同步 SQLite 阻塞事件循环
`db.ts:19-35` 用 `async` 包裹同步的 `DatabaseSync`（`prepare/run/all/get`），全部调用实为主线程阻塞操作。叠加 `documents.ts:58-63` 的**逐条 `await run(INSERT)`**（一个 5MB 文档可产生上千次同步写），在流式回答进行中上传文档，会直接卡住正在推送的 SSE 帧。
**改法**：批量插入改为单条多值 INSERT 并包事务（`BEGIN`/`COMMIT`）；解析、分块、向量化等长任务移入 `worker_threads`。
**验证**：一边流式问答、一边上传 10MB PDF，统计 SSE 帧间隔的 P99。

### M2. 文档写入无事务 → 失败文档的半截片段仍可被检索
`documents.ts:58-65` 的 chunks 逐条插入与状态更新无事务。中途失败时 `38-39` 行把文档置为 `failed`，但**已插入的 chunks 保留**；而 `vector.ts:44-46` 的检索只按 `embedding IS NOT NULL` 过滤，**不校验文档状态** → 失败文档的部分内容仍会进入 RAG 上下文。
**改法**：写入包事务；或 `searchSimilar` 增加 `JOIN documents d ON d.id = c.documentId AND d.status = 'ready'`；失败时清理该 docId 的 chunks。
**验证**：构造一个解析中途失败的文档，断言 `/api/documents/search` 不再命中其片段。

### M3. 超时/重试策略未显式设定
已核实依赖默认值（`backend/node_modules/openai/core.mjs:131`）：`maxRetries = 2`、`timeout = 600000`（10 分钟）。即**重试存在但超时长达 10 分钟且不可控**；`embedding.ts:33-39` 按 16 条一批**串行**执行，大文档可长时间占住进程；文档处理失败后无重试入口（`documents.ts:37-39` 一次置 failed）。
**改法**：显式传入 `{ timeout, maxRetries }`；对 429/5xx 指数退避；`embedding` 批次改为有限并发；新增 `POST /api/documents/:id/retry`。
**验证**：mock 一个持续 500 的 embedding 端点，断言重试次数有界且最终状态为 `failed`，而非挂满 10 分钟。

### M4. 空 catch 吞掉检索失败，静默降级为普通对话
`chat.ts:70-77` 为 `catch (e) { /* 注释 */ }`，无日志、无上报、无用户提示。用户已在 `ChatView.vue:26-42` 选择 RAG 模式（"RAG 模式"标签仍显示），但实际走了 `98` 行的普通 system prompt，答案与知识库无关却无任何标识——掩盖幻觉来源。
**改法**：至少 `console.error`；新增 SSE `degraded` 事件把降级原因下发，UI 明确提示"检索失败，已按普通对话回答"。
**验证**：故意填错 embedding key，断言 UI 出现降级提示而非静默通过。

### M5. 轮询定时器无生命周期管理；卡死的 `processing` 导致无限轮询
`stores/docs.ts:29-39` 在 Pinia store 内 `setInterval` 且**无人清理**（store 与 app 同生命周期）；`db.ts:38-84` 的 `initDB` **不重置残留状态**，若处理途中进程被杀，文档永久停留 `processing` → 每次进入知识库页都触发一次永久性的 2s 轮询。
**改法**：启动时把残留 `processing` 重置为 `failed`（或加 `updatedAt` 超时判定）；轮询改 `setTimeout` 递归并在组件 unmount 时停止。
**验证**：在 `processing` 状态强杀进程后重启，断言不再持续轮询。

### M6. 同会话并发发送存在竞态
`chat.ts:64-66` 插入 user 消息与 `88-92` 读取历史之间无隔离；同会话并发两次 `/send`（双击、双标签页）会互相把对方的消息读进上下文。前端 `stores/chat.ts:71` 的 `this.streaming` 仅是本实例的单点守卫。
**改法**：服务端按 `conversationId` 串行化（内存队列/mutex），或把插入与读取放入同一事务并显式排除未完成消息。
**验证**：并发脚本对同一 `conversationId` 同时发起两次 `/send`，校验历史顺序与内容一致性。

### M7. 缺参数校验导致 500 而非 400
`chat.ts:45-49` 未校验 `conversationId`。实测 node:sqlite 行为：绑定 `undefined` 抛 `TypeError: Provided value cannot be bound to SQLite parameter 1.`，绑定 `null` 抛 `NOT NULL constraint failed`——两者都会落到 `118-121` 行的 catch，在**已发送 SSE 头的 200 响应**里下发 error 事件，而非干净的 400。
**改法**：入口校验 `Number.isInteger(conversationId)` 且会话存在，否则 400；对所有路径参数（`req.params.id`）同样处理。
**验证**：`POST /api/chat/send` 不带 `conversationId`，断言返回 400 且不含 SSE 头。

# 一、项目整体

## Q1. 用一句话介绍这个项目

**答：**
这是一个基于 **RAG（检索增强生成）** 的智能知识库问答系统。用户上传 PDF、Word、Markdown 等文档后，系统自动解析、分块、向量化；用户提问时先从知识库检索出最相关的内容片段，再让大模型基于这些片段生成带来源引用的回答，并支持打字机式的流式输出。

**为什么做（动机可以说）：**
想把当前主流的大模型落地技术（RAG）和自己的前端/Vue 技术栈结合，做一个前后端都能讲清楚、不是单纯"调 API"的全栈项目。

## Q3. 什么是 RAG？为什么需要它

**答：**
RAG（Retrieval-Augmented Generation，检索增强生成）= **先检索、再生成**。在调用大模型之前，先从外部知识库里检索出与问题相关的内容，把这些内容作为上下文喂给模型，让模型"看着资料回答"。

**为什么需要：**

1. **知识时效 / 私有数据**：大模型的训练数据有截止日期，也不知道你公司/个人的私有文档。RAG 可以接入实时和私有的知识。
2. **成本**：相比重新训练/微调模型，更新知识库只是换数据，便宜得多。
3. **可溯源、降幻觉**：回答基于给定材料，还能标注出处，比让模型"凭空回忆"可靠。

---

## Q4. RAG vs 微调（Fine-tuning）

**答：**

| 维度 | RAG | Fine-tuning |
|---|---|---|
| 解决的问题 | 知识从哪来（事实、数据） | 模型怎么表现（风格、语气、格式） |
| 更新成本 | 低，更新知识库即可 | 高，要重新训练 |
| 可解释性 | 强，能给出来源 | 弱 |
| 幻觉 | 相对低 | 仍可能 |
| 适用 | 私有/实时知识问答 | 固定风格、特定领域行为 |

**结论：** 两者不是互斥的。我的项目解决的是"基于私有文档回答"，所以用 RAG；如果还要求模型统一某种输出风格，可以在 RAG 基础上叠加微调。

---

## Q5. 你独立负责了什么 / 最难的点

**答（挑真实的、有技术含量的说）：**

- 从架构设计、前后端开发到联调全部独立完成。
- **最难/最有收获的是流式问答这一块**：原生 `EventSource` 不支持 POST 请求和自定义 header，我用 `fetch + ReadableStream` 手写了 SSE 解析，并处理了流式数据的半包/粘包问题，还用 AbortController 实现了中断生成。
- 另一个难点是**把 RAG 链路的工程细节做扎实**：异步入库、状态轮询、相似度阈值过滤、embedding 失败时降级为普通对话等。

> 提示：说"最难"时要落到具体技术和解决思路，不要说"都挺难的"。

# 二、文档处理链路

## Q6. 文档上传后经历了哪些步骤

**代码：** `backend/src/routes/documents.ts`

```ts
// 文档处理核心流程：解析 → 分块 → 向量化 → 入库
async function processDocument(docId, fileName, buffer) {
  // 1. 解析文本
  const text = await parseDocument(fileName, buffer)
  if (!text.trim()) throw new Error('文档内容为空，可能是扫描件或解析失败')

  // 2. 分块
  const chunks = splitText(text, chunkSize, chunkOverlap)
  if (chunks.length === 0) throw new Error('分块结果为空')

  // 3. 向量化
  const embeddings = await embedTexts(chunks)

  // 4. 写入数据库
  for (let i = 0; i < chunks.length; i++) {
    await run('INSERT INTO chunks (...) VALUES (?, ?, ?, ?)',
      [docId, i, chunks[i], JSON.stringify(embeddings[i])])
  }
  await run('UPDATE documents SET status = ?, chunkCount = ? WHERE id = ?',
    ['ready', chunks.length, docId])
}
```

**答：** 四步——**解析 → 分块 → 向量化 → 持久化**。文档状态从 `processing` 变成 `ready`，失败则置为 `failed` 并记录错误信息。

---

## Q7. 为什么要分块（Chunking）

**答：**

1. **模型上下文长度有限**：不能把一整份长文档全塞进去。
2. **检索更精准**：用户问题只跟文档的一小部分相关。切成小块后做向量检索，命中的是"具体相关段落"，而不是整篇，能减少无关内容（噪声）。
3. **成本**：按相关片段计费/处理，而不是全文。

---

## Q8. 分块为什么要重叠（overlap）⭐高频

**代码：** `backend/src/services/splitter.ts`

```ts
while (start < clean.length) {
  const end = Math.min(start + chunkSize, clean.length)
  chunks.push(clean.slice(start, end))
  if (end >= clean.length) break
  start = end - overlap // 回退一段，制造重叠
}
```

**答：**
切块的边界是"硬切"的，很可能把一个完整的句子、一个语义单元从中间切断，导致某个片段语义不完整。让相邻片段保留一段重叠（overlap），可以保证跨边界的关键信息至少完整地出现在其中一个片段里，提升检索召回的完整性。

**追问：重叠是不是越大越好？**
不是。重叠太大会造成大量冗余：片段数量变多、向量存储和计算成本上升，检索时还会反复命中高度重复的内容。通常取 chunkSize 的 10%~20%（我这里 500/80 ≈ 16%）。

---

## Q9. chunkSize / overlap 怎么取舍

**答：**

- **chunkSize 太小**：语义不完整，向量表达不了完整含义，检索可能漏。
- **chunkSize 太大**：一个块里塞了多个主题，向量被"平均稀释"，检索不精准，还浪费上下文空间。
- 经验值：中文按字符大约 300~800，配合 10%~20% 重叠。
- **关键是可配置 + 按效果调**：我把这两个参数做成了可在设置页配置（存 `settings` 表），可以根据实际文档类型和检索效果调优，而不是写死。

---

## Q10. 按字符切有什么缺陷，怎么改进 ⭐

**答（这题答得好能体现思考深度）：**
我现在是**固定字符数滑动窗口切分**，简单通用，但缺陷是：它不理解文档结构，可能从标题和正文之间、句子中间切开。

**改进方向（按优先级）：**

1. **优先按语义/结构边界切**：先按 Markdown 标题、段落、换行做"递归切分"，尽量在自然边界断开，超长了再退化为字符切。这是 LangChain `RecursiveCharacterTextSplitter` 的思路。
2. **按句子切**：用句号、问号等标点断句，再把句子组合到目标长度。
3. **特殊结构特殊处理**：代码块、表格不要被切碎，可以整段保留。
4. 更进阶可以用"父子分块"：用小块做检索（精准），实际喂给模型时返回它所属的大块/父块（上下文完整）。

## Q11. PDF / DOCX 是怎么解析的

**代码：** `backend/src/services/parser.ts`

```ts
import mammoth from 'mammoth'
const pdfParse = require('pdf-parse/lib/pdf-parse.js')

export async function parseDocument(fileName, buffer) {
  const ext = fileName.split('.').pop()?.toLowerCase()
  switch (ext) {
    case 'txt':
    case 'md':  return buffer.toString('utf-8')
    case 'pdf': { const data = await pdfParse(buffer); return data.text || '' }
    case 'docx': { const result = await mammoth.extractRawText({ buffer }); return result.value || '' }
    default: throw new Error(`暂不支持的文件格式：.${ext}`)
  }
}
```

**答：**

- txt / md：直接按 UTF-8 转字符串。
- PDF：用 `pdf-parse` 提取文本层。
- DOCX：用 `mammoth` 提取纯文本。
- 用 `createRequire` 引入 pdf-parse，是因为它是 CommonJS 包，在 ESM 项目里直接 import 有兼容问题；并且引用 `lib/pdf-parse.js` 避免默认入口去读取它自带的测试 PDF。

## Q12. 扫描件 PDF 为什么解析不出内容

**答：**
PDF 分两种：

- **文字版 PDF**：里面存的是真实的文字编码，pdf-parse 能直接提取。
- **扫描件 / 图片版 PDF**：每一页其实是一张图片，没有文字层，pdf-parse 提取不到任何文字，所以我代码里会判断 `!text.trim()` 并抛出"文档内容为空"。

**怎么解决：** 加一层 **OCR**（光学字符识别），先把图片中的文字识别出来。可以用 Tesseract、或带视觉能力的多模态模型/云 OCR 服务。这是我项目目前明确的一个待增强点。

# 三、Embedding 与向量化

## Q13. 什么是 Embedding，文本怎么变成向量

**答：**
Embedding（嵌入）是把文本（词、句子、段落）映射成一个**高维浮点数组**（向量），例如 bge-m3 是 1024 维。语义相近的文本，在向量空间里距离也近。

例如（仅示意）：

```
"如何退货"  -> [0.12, -0.03, 0.88, ...]   // 1024 维
"怎么退款"  -> [0.11, -0.02, 0.86, ...]   // 语义近 → 向量近
"今天天气"  -> [-0.7, 0.5, ...]           // 语义远 → 向量远
```

这样"检索相关内容"就转化成了"计算向量之间的距离"。

---

## Q14. Embedding 接口怎么调用，为什么分批

**代码：** `backend/src/services/embedding.ts`

```ts
const batchSize = 16

export async function embedTexts(texts: string[]): Promise<number[][]> {
  const client = new OpenAI({ apiKey, baseURL: baseUrl })
  const result: number[][] = []
  for (let i = 0; i < texts.length; i += batchSize) {
    const batch = texts.slice(i, i + batchSize)
    const resp = await client.embeddings.create({ model, input: batch })
    const sorted = resp.data.sort((a, b) => a.index - b.index)
    for (const item of sorted) result.push(item.embedding)
  }
  return result
}
```

**答：**

- 用 OpenAI SDK 的 `embeddings.create`，`input` 支持传数组，一次处理多条。
- **分批（batch）**：单次请求文本太多会超出接口的长度/数量限制，也容易超时或失败；分批更稳。
- **按 `index` 排序**：接口返回顺序不保证和输入一致，按 index 排序确保向量和文本一一对应。

---

## Q15. 为什么换 Embedding 模型必须重建数据 ⭐

**答：**
不同 Embedding 模型：

1. **向量维度可能不同**（如有的 768、有的 1024、有的 1536），维度不同根本无法一起计算相似度。
2. 即使维度相同，**各自的向量空间定义也不同**——A 模型和 B 模型对"语义"的编码方式没有可比性，混在一起算余弦相似度没有意义。

所以一旦更换 Embedding 模型，必须把所有历史片段用新模型**重新向量化（重建索引）**。这也是为什么我在使用注意里强调"一开始定好模型别中途换"。

---

## Q16. bge-m3 是什么，为什么选它

**答：**
bge-m3 是智源研究院（BAAI）开源的多语言、多功能 Embedding 模型，中文效果好、支持长文本（8192 token），输出 1024 维。我通过硅基流动（SiliconFlow）的 API 使用它，该服务对 bge-m3 提供免费调用，零成本就能跑通；而且它是 OpenAI 兼容接口，接入简单。

# 四、向量检索

## Q17. 语义检索是怎么实现的

**代码：** `backend/src/services/vector.ts`

```ts
export async function searchSimilar(queryVec, topK, docId?) {
  const rows = docId
    ? await all('SELECT * FROM chunks WHERE documentId = ? AND embedding IS NOT NULL', [docId])
    : await all('SELECT * FROM chunks WHERE embedding IS NOT NULL')

  const scored = rows.map(row => {
    const vec = JSON.parse(row.embedding)
    return { ..., score: cosineSimilarity(queryVec, vec) }
  })
  return scored.sort((a, b) => b.score - a.score).slice(0, topK)
}
```

**答：**
把问题向量化后，取出知识库中所有片段的向量，逐个与问题向量算余弦相似度，按分数从高到低排序，取前 K 个。可以传 `docId` 限定只检索某个文档。

---

## Q18. 余弦相似度原理，手写一遍 ⭐高频

**代码：** `backend/src/services/vector.ts`

```ts
export function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, normA = 0, normB = 0
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i]
    normA += a[i] * a[i]
    normB += b[i] * b[i]
  }
  if (normA === 0 || normB === 0) return 0
  return dot / (Math.sqrt(normA) * Math.sqrt(normB))
}
```

**讲解：**
余弦相似度衡量两个向量方向的夹角：

```
cosθ = (A·B) / (|A| × |B|)
```

- `A·B` 是点积（对应位置相乘再求和）
- `|A|`、`|B|` 是各自的模长（L2 范数）
- 结果范围 -1 ~ 1，越接近 1 表示方向越一致、语义越相近。

**追问：为什么用余弦而不是欧氏距离？**
余弦只看方向（语义），对向量的绝对长度不敏感，更适合文本相似度；而且很多 embedding 模型输出已归一化，此时余弦相似度和点积等价。我代码里还做了 norm 为 0 的保护，避免除零。

## Q19. 为什么用相似度阈值 0.3

**代码：** `backend/src/routes/chat.ts`

```ts
sources = sources.filter(s => s.score > 0.3) // 相似度阈值，过滤无关结果
```

**答：**
Top-K 是"硬取 K 个"，哪怕库里没有相关内容，也会硬凑出 K 个分数很低的片段。加一个相似度阈值，把明显不相关的结果过滤掉：

- 过滤后**还有** sources → 走 RAG；
- 过滤后**为空** → 说明知识库里没有相关内容，就不注入无关上下文（避免误导模型），降级为普通对话。

阈值是经验值，需要结合实际 embedding 模型和数据来调，太低会放进噪声，太高会漏掉结果。

---

## Q20. Top-K 是什么，K 越大越好吗

**答：**
Top-K 指检索时返回相似度最高的 K 个片段。

- **K 太小**：可能漏掉有用信息，回答不全。
- **K 太大**：塞进 Prompt 的上下文变长，增加 token 成本和延迟；无关内容变多还可能"淹没"真正关键的信息（lost in the middle 问题），反而影响回答质量。
- 通常取 3~5，我默认 4 且做成可配置。

---

## Q21. 你这算向量数据库吗？和真正的向量库区别 ⭐

**答（要诚实，别硬吹）：**
严格说**不算专业向量数据库**。我是把向量以 JSON 字符串存在 SQLite 的普通字段里，检索时全部读出来、在应用内存里逐个算相似度。它能让我完整理解 RAG 的检索原理，适合 Demo 规模。

**专业向量数据库（pgvector、Milvus、Chroma、Qdrant 等）的区别：**

1. **近似最近邻索引（ANN，如 HNSW、IVF）**：不用全量扫描也能快速找 Top-K。我的做法是全量暴力计算，复杂度 O(N)。
2. **专用存储结构和高维优化**，支持百万/亿级向量。
3. 通常自带元数据过滤、混合检索等能力。

**一句话总结：** 我实现的是"向量检索的原理"，专业库解决的是"大规模下的性能"。

---

## Q22. 数据量大了，你这套检索的瓶颈和优化 ⭐⭐加分

**答（开放题，按层次答）：**

**瓶颈：** 现在是"全量取出 + 内存逐对计算"，复杂度 O(N×D)。片段数 N 一大：内存占用高、计算慢，SQLite 字段里反复 parse JSON 也有开销。

**优化路径：**

1. **上专业向量存储**：PostgreSQL + **pgvector**（加 HNSW/IVFFlat 索引，改动最小），或 Milvus / Qdrant，把检索复杂度从全量扫描降到 ANN 近似查询。
2. **检索与重排分离**：先粗召回较多候选（如 Top-50），再用 Rerank 模型精排到 Top-4，兼顾召回率和精准度。
3. **混合检索**：向量检索 + BM25 关键词检索，用 RRF 融合，解决向量检索对专有名词、编号、精确匹配不敏感的问题。
4. **预处理/工程优化**：向量用二进制（BLOB/Float32Array）存储而非 JSON 字符串，省空间、解析更快；加缓存。
5. **元数据预过滤**：先按文档/分类缩小范围，再做向量检索。

> 这题是区分"只会用"和"懂工程"的关键，建议背熟。

## Q24. 怎么降低大模型幻觉 ⭐高频

**答（结合代码，多层手段）：**

1. **提供可靠上下文**：让模型基于检索片段作答，而不是自由回忆——这是 RAG 的根本作用。
2. **Prompt 强约束**：明确"只能用参考片段信息、不许编造"（rag.ts 第 1 条）。
3. **给"拒答"出口**：信息不足时要求直接说"无法回答"，而不是硬编（第 2 条）。
4. **检索质量控制**：相似度阈值过滤 + Top-K，避免无关/低质片段误导模型。
5. **来源引用**：要求标注 [1][2]，答案可与原文核对，既方便用户验证，也约束模型。

**可以补充：** 没有任何手段能 100% 消除幻觉，工程上是"显著降低 + 可溯源核对"。

## Q26. 多轮对话的上下文是怎么处理的 ⭐

**代码：** `backend/src/routes/chat.ts`

```ts
const history = await all(
  `SELECT role, content FROM messages WHERE conversationId = ? ORDER BY id DESC LIMIT 20`,
  [conversationId])
history.reverse()

const messages = []
messages.push({ role: 'system', content: ... })   // 每轮重新拼 system + 检索结果
for (const h of history) messages.push({ role: h.role, content: h.content })
```

**答：**
我采用**服务端无状态 + 前端/数据库携带历史**的方式：每次提问，从数据库取出该会话最近的消息（这里取最近 20 条，做滑动窗口），连同本轮新的 system prompt（含当轮检索结果）一起重新组装发给 LLM。

**追问：为什么只取最近 N 条？**
控制 token、避免超出上下文窗口和成本膨胀，同时太老的历史相关性也低。这是滑动窗口记忆；更复杂可以做历史摘要压缩。

# 六、SSE 流式输出（前端核心亮点）

## Q27. 什么是 SSE，和 WebSocket 区别 ⭐⭐高频

**答：**
SSE（Server-Sent Events）是基于 HTTP 的**服务器到客户端单向推送**技术，服务器持续往一个长连接里写 `text/event-stream` 格式的数据。

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务器 → 客户端，单向 | 全双工，双向 |
| 协议 | 普通 HTTP | 独立的 ws/wss 协议 |
| 数据 | 文本（默认 UTF-8） | 文本 + 二进制 |
| 断线 | 浏览器内置自动重连 | 需自己实现 |
| 适用 | 通知、流式输出、股票行情 | 聊天 IM、协同编辑、游戏等强交互 |

**为什么这里选 SSE：** AI 问答是典型的"服务器源源不断推送 token、客户端基本只接收"，单向、基于 HTTP、轻量、实现简单，SSE 非常契合；不需要 WebSocket 的双向能力。

---

## Q28. 为什么不用原生 EventSource ⭐

**答：**
浏览器原生 `EventSource` 只能发 **GET** 请求，不能带请求体（body），也不方便自定义 header。

而我的问答接口设计成 **POST + JSON**（要传 conversationId、message、docId），原生 EventSource 用不了。所以我用 `fetch`（支持 POST）拿到响应流，再用 `ReadableStream` 手动按 SSE 协议解析。

---

## Q29. 后端 SSE 怎么写的

**代码：** `backend/src/routes/chat.ts`

```ts
res.setHeader('Content-Type', 'text/event-stream')
res.setHeader('Cache-Control', 'no-cache')
res.setHeader('Connection', 'keep-alive')

const send = (event, data) => {
  res.write(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`)
}

send('sources', ...)   // 先推来源
await streamChat(messages, (delta) => send('delta', { content: delta })) // 逐 token 推
send('done', ...)
res.end()
```

**答：** 设置好 SSE 响应头后，用 `res.write` 按 `event: xxx\ndata: xxx\n\n` 的格式持续写入，事件分 `sources → delta(多次) → done`，出错发 `error`，最后 `res.end()`。

**追问：两个 `\n\n` 的作用？** 一个空行表示一个事件的结束，是 SSE 协议规定的分隔符，前端据此切分事件。

## Q30. 前端怎么解析 SSE（fetch + ReadableStream）⭐⭐

**代码：** `frontend/src/api/sse.ts`

```ts
const resp = await fetch('/api/chat/send', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(payload),
  signal: controller.signal,
})
const reader = resp.body.getReader()
const decoder = new TextDecoder('utf-8')
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })

  const events = buffer.split('\n\n')
  buffer = events.pop() // 最后一段可能不完整，留到下次

  for (const evt of events) {
    let event = 'message', dataStr = ''
    for (const line of evt.split('\n')) {
      if (line.startsWith('event:')) event = line.slice(6).trim()
      else if (line.startsWith('data:')) dataStr += line.slice(5).trim()
    }
    const data = JSON.parse(dataStr)
    // 按 event 类型分别处理 sources / delta / done / error
  }
}
```

**答：** fetch 返回的响应有一个可读流，用 reader 不断读取二进制块，TextDecoder 解码成字符串，再按 SSE 协议解析出事件类型和数据，回调给上层做增量渲染。

## Q31. 「停止生成」怎么实现的（AbortController）

**代码：**

- 前端 `sse.ts`：`const controller = new AbortController()`，fetch 传入 `signal: controller.signal`，对外返回 `() => controller.abort()`。
- store `chat.ts`：

```ts
stopStreaming(abortRef) {
  abortRef?.fn?.()                 // 调用 abort，中断 fetch
  this.streaming = false

}
```

**答：** 用 AbortController 中止 fetch 请求和底层连接；已经收到的部分回答保留，界面退出 streaming 状态。发送/停止按钮根据 `streaming` 状态切换。

## Q32. 流式数据半包/粘包怎么处理 ⭐

**答：**
网络是分块到达的，不能假设一次 read 拿到完整事件：

- **半包**：一次只读到半个事件 → 我把 `split('\n\n')` 的最后一段（`events.pop()`）留在 `buffer`，等下次数据来了拼接。
- **粘包**：一次读到多个事件 → `split('\n\n')` 会得到多个完整事件，循环逐个处理。
- 用 `decoder.decode(value, { stream: true })`，`stream:true` 保证跨块的多字节字符（如中文，UTF-8 可能占 3 字节且被切到两个块）不会被错误解码。

这是流式解析最容易被忽略、也最能体现严谨性的点。

## Q33. 为什么用打字机效果，体验好在哪

**答：**

1. **首字等待短**：不用等整段话生成完才显示，用户很快看到反馈，感知延迟大幅降低。
2. **过程可观察**：能看到模型"边想边写"，长回答也不会长时间白屏。
3. **可提前中断**：发现答偏了可以立刻停止，省时间省 token。

# 七、架构、工程与容错

## Q34. 为什么用 SQLite / node:sqlite

**答：**

- Demo 规模下 SQLite 是单文件、零安装、零外部服务，最容易本地跑通和演示。
- 我用的是 **Node 内置的 `node:sqlite`**，不需要安装 `sqlite3` 这类要 node-gyp 编译的原生模块——这正是我一开始在 Windows 上踩的坑（原生模块编译失败），换成内置库后零编译。
- 数据模型（文档、片段、会话、消息、键值配置）关系清晰，用关系型表 + 外键级联删除很合适。

## Q35. node:sqlite 是同步的，会阻塞事件循环吗 ⭐

**答：**
会，`DatabaseSync` 的 API 是同步的，执行期间会阻塞 Node 事件循环。但在我这个场景：

- 数据量小（Demo 级），单条 SQL 执行是毫秒甚至微秒级，阻塞可忽略。
- 真正耗时的是 **embedding / LLM 的网络请求**，那部分用的是异步 API（`await`），不会被数据库同步调用影响。

如果数据/并发变大，就应该改用异步数据库驱动或专业服务，避免同步 SQL 在高并发下阻塞。这是我清楚的权衡。

## Q36. 文档为什么做成异步入库 + 轮询

**代码：** `backend/src/routes/documents.ts`

```ts
// 先响应，后台异步处理
res.json({ code: 0, data: { id: lastID, name: file.originalname } })
processDocument(lastID, file.originalname, file.buffer).catch(err => {
  run('UPDATE documents SET status = ?, errorMsg = ? WHERE id = ?', ['failed', err.message, lastID])
```

前端 `stores/docs.ts` 每 2 秒轮询，直到状态变 ready/failed。

**答：**
文档解析、分块、批量向量化比较耗时（可能几秒到几十秒），如果让 HTTP 请求一直挂着，容易超时、体验差、还可能被网关断开。所以：

- 接口收到文件先落库（status=processing）并**立即返回**；
- 后台异步处理，处理结果回写状态；
- 前端轮询状态实时展示"处理中/已完成/失败"，失败还能看到原因。

这是典型的"异步任务 + 状态查询"模式。生产上可升级为消息队列 + WebSocket/SSE 推送终态。

## Q37. 项目里有哪些降级容错设计 ⭐

**答（结合代码列举）：**

1. **embedding/检索失败不阻塞问答**：chat.ts 里检索包了 try/catch，失败时 sources 为空，降级为普通对话。
2. **无相关知识时降级**：相似度阈值过滤后为空，就不注入 RAG context，用通用 system prompt。
3. **入库失败有记录**：processDocument catch 后把文档置为 failed 并保存 errorMsg，前端能展示，不会"静默消失"。
4. **相似度计算防除零**：norm 为 0 返回 0。
5. **SSE 错误事件**：生成过程出错会发 `error` 事件，前端提示并退出 loading。
6. **用户主动中断与异常区分**：AbortError 单独处理。

# 八、前端原理（结合本项目的 Vue 八股）

## Q41. Pinia 状态怎么组织的

**答：** 按业务域拆三个 store：

- `useChatStore`：会话列表、当前会话、消息、streaming 状态，以及发消息/切换/删除等 action。
- `useDocsStore`：文档列表、选中文档、轮询定时器、上传/删除/检索。
- `useSettingsStore`：配置表单、读取/保存。

状态和操作状态的方法封装在同一个 store 里，组件通过 action 改状态、不直接散落逻辑。

**追问：Pinia 和 Vuex 区别？** 没有 mutations、TS 支持更好、支持组合式写法、扁平化无需嵌套模块、更轻量。

## Q42. Vue3 响应式原理 / 流式内容为什么能实时更新

**答：**
Vue3 用 **Proxy** 拦截对象的读/写（Vue2 用 Object.defineProperty 只能劫持已有属性）。组件渲染时读取响应式数据会建立依赖，数据变化时触发对应的更新。

在我的流式场景里，每个 delta 到达就执行 `aiMsg.content += delta`，这个 `content` 是响应式的，修改后视图自动重新渲染，所以文字能"逐字蹦出来"。

**追问：Proxy 相比 defineProperty 的优势？** 能监听新增/删除属性、能代理数组和嵌套对象、性能更好（惰性代理）。

## Q43. watch 和 watchEffect 区别（结合自动滚动）

**代码：** `frontend/src/views/ChatView.vue`

```ts
watch(() => chatStore.messages.length, scrollBottom)
watch(() => chatStore.messages[chatStore.messages.length - 1]?.content, scrollBottom)
```

**答：**

- `watch`：明确指定要监听的数据源，能拿到新旧值，惰性触发（默认要变化才执行）。
- `watchEffect`：自动收集回调里用到的所有依赖，立即执行一次。

我用 `watch` 监听"消息数量"和"最后一条消息的内容"（流式时内容持续变），变化时把列表滚到底部。监听最后一条的 content 是关键，因为流式追加内容时消息数量不变、只有内容变。

## Q44. nextTick 用在哪、为什么

**代码：** `ChatView.vue` 的 `scrollBottom`

```ts
function scrollBottom() {
  nextTick(() => {
    if (msgListRef.value) msgListRef.value.scrollTop = msgListRef.value.scrollHeight
  })
}
```

**答：** Vue 的 DOM 更新是异步批量执行的。改完数据后真实 DOM 还没立刻更新，`nextTick` 能让回调在 DOM 更新完成后执行。我要在消息渲染出来后再去读 scrollHeight 并滚动，所以要放进 nextTick，否则拿到的可能是更新前的高度。

## Q45. v-html 渲染 Markdown 有 XSS 风险吗 ⭐

**代码：** ChatView 用 `v-html="renderMd(msg.content)"`，markdown-it 配置 `html: false`。

**答：**
有潜在风险。`v-html` 会把字符串当 HTML 渲染，如果内容里混入恶意 `<script>`/事件属性，可能造成 XSS。我的缓解：

1. markdown-it 设置 **`html: false`**，不允许原文里的 HTML 标签被直接输出。
2. 内容主要来自 AI 基于知识库的回答，不是任意用户直接写的 HTML。

**更严谨的做法（可以作为优化说）：** 增加 **DOMPurify** 对渲染结果做一次 sanitize 再 v-html，这是生产标准做法。但要注意：在 AI 对话场景也不能完全信任模型输出。

2. **混合检索 + Rerank**，提升召回和精准度。
3. **OCR** 支持扫描件和图片。
4. **会话能力增强**：对话重命名、搜索历史、导出、消息编辑重发、分享。
5. **工程化**：用户鉴权、缓存（语义缓存）、可观测性（trace 各阶段耗时）、容器化部署。
6. 上 pgvector / 专用向量库支撑大规模。

---

## Q47. 如何引入混合检索（向量 + 关键词）

**答：**
向量检索擅长语义，但对专有名词、编号、精确短语不敏感；BM25 关键词检索正好互补。

做法：分别用向量检索和 BM25 各召回一批，再用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 按各自排名（而非分数量纲）融合排序。这样不用关心两种分数的尺度差异，工程上简单有效。

---

## Q48. 如何加 Rerank 重排序

**答：**
Embedding 检索为了快，用的是双编码器（query 和 doc 分别编码算相似度）。Rerank 用**交叉编码器（cross-encoder）**，把 query 和每个候选拼在一起让模型直接打分，更准但更慢。

所以标准模式是"**两阶段**"：第一阶段向量快速粗召回 Top-50，第二阶段用 rerank 模型对这 50 个精排，取 Top-4 喂给 LLM。兼顾速度和精度（如 bge-reranker）。

---

## Q49. 怎么做权限 / 多用户

**答：**

- 加用户表、注册登录，密码加盐哈希存储。
- 用 **JWT/Session** 鉴权，接口加鉴权中间件。
- 所有业务表加 `userId`，查询时按用户过滤，保证数据隔离；文档/片段/会话都归属用户。
- 前端做路由守卫（未登录跳转）、按钮级权限。
- 我的项目刻意砍掉了这部分以聚焦 RAG 核心，但设计上预留了扩展方式。

## Q50. 生产部署要注意什么

**答：**

1. **鉴权和限流**：当前接口完全开放，公网暴露会被人盗用消耗 LLM 配额，必须加认证 + 速率限制 + 网关。
2. **HTTPS / 反向代理（Nginx）**，注意代理要关掉 buffering，否则 SSE 会被缓冲、打字机失效。
3. **密钥管理**：API Key 放环境变量/密钥服务，不写进代码和前端。
4. **数据库**：备份、换成异步驱动/专业向量库、连接池。
5. **异步任务**：上消息队列处理入库，替代简单轮询。
6. **可观测性**：日志、监控、错误追踪、RAG 各阶段耗时。
7. **资源与成本**：LLM 调用的成本和超时控制、重试与熔断。

# 附录 A：一句话速记（面试前 5 分钟扫一遍）

- **RAG** = 先检索相关片段，再让模型看着资料回答；解决知识时效/私有数据/成本/可溯源。
- **分块重叠** = 防止语义在切块边界被截断；重叠 ≈ chunkSize 的 10~20%。
- **Embedding** = 文本 → 高维向量；语义近则向量近。换模型必须重建（维度/空间不同）。
- **余弦相似度** = 点积 / 模长乘积，只看方向；范围 -1~1。
- **Top-K + 阈值** = 取最相关 K 个，再用阈值剔除无关；K 太大淹没关键信息。
- **降幻觉** = 给上下文 + Prompt 约束 + 给拒答出口 + 阈值过滤 + 来源引用。
- **SSE** = HTTP 单向服务器推送；EventSource 只支持 GET，故用 fetch+ReadableStream。
- **半包/粘包** = 留 buffer 拼半包，split('\n\n') 拆多事件，TextDecoder stream:true。
- **停止生成** = AbortController.abort()，区分 AbortError。
- **多轮** = 服务端无状态，每轮取最近 N 条历史 + 重新检索拼 system。
- **瓶颈/优化** = 全量内存 O(N) → pgvector/ANN、混合检索、Rerank、向量二进制存储。

## 一、阻断问题（4/4 已修复）

### B1 分块函数死循环 → `backend/src/services/splitter.ts`

| 项 | 内容 |
|----|------|
| 修改 | 循环步进改为 `start = end - ov`，其中 `ov` 经 `clampInt(overlap, 80, 0, size - 1)` 收敛；`size` 收敛到 `[1, 10000]`。`clampInt` 对回退值同样做区间收敛 |
| 理由 | 原实现前进量为 `chunkSize - overlap`，`overlap >= chunkSize` 时非正，循环条件恒真 |
| 配套 | `routes/config.ts` 增加跨字段校验：`chunkOverlap < chunkSize`，否则 400（配置侧第二道防线） |
| 验证 | `test/splitter.test.mts`：12 组边界参数（含原崩溃用例 `100/500`、`500/500`、`NaN`、负数、极大值）全部在 500ms 内返回且结果正确；接口测试断言 `chunkSize=100, chunkOverlap=500` 返回 400 |

实现过程中自查发现并修正：`clampInt` 初版对 `NaN` 输入直接返回未收敛的 fallback，`splitText(text, 50)`（overlap 缺省 80 > size-1）仍会死循环。已改为回退值同样参与收敛，并补入测试用例。

### B2 流式渲染失效 → `frontend/src/stores/chat.ts`

| 项 | 内容 |
|----|------|
| 修改 | 先 `push` 占位消息，再通过 `this.messages[this.messages.length - 1]` 取回**响应式代理**引用，回调中只改该引用 |
| 理由 | 原实现把裸对象存入 store 后直接改它，绕过了 reactive 的 `set` trap，不触发 `trigger` |
| 验证 | 用真实 Pinia + `effect` 复现修复后的同构 action：渲染快照序列为 `(empty)→user:"hi"→assistant:""[光标]→"你"→"你好"→"你好，"→…→"你好，世界"`，出现逐字中间态；修复前中间态数量为 0 |

### B3 断开不中止上游 + 落库不一致 → `backend/src/routes/chat.ts`、`services/llm.ts`

| 项 | 内容 |
|----|------|
| 修改 | 用 `res.on('close')` 配合 `!res.writableFinished` 判定客户端断开，触发 `AbortController`；signal 透传到 `streamChat` 的 `RequestOptions`；助手消息改为在生成结束后**无条件落库**，并区分「正常 / 已停止生成 / 生成失败」三种文案 |
| 理由 | 原先无任何断开感知；用户消息先入库、助手回复仅在正常结束时入库，中止即留下孤立提问 |
| 实现要点 | **实测发现 `req.on('close')` 在正常请求下 4ms 就触发**（`writableFinished=false`），若照此实现会立刻误中止自己的 LLM 调用。故改用 `res` 的 `close`：正常结束 `writableFinished=true`，客户端断开 `false` |
| 验证 | 接口测试断言「生成失败」场景下消息表仍为 2 条（user + assistant）且助手侧带明确标记；另实测确认断开后服务端继续写入不会打崩进程（属静默失败，故定性为数据一致性问题） |

### B4 权限边界 → `backend/src/index.ts`、`routes/config.ts`、`src/config.ts`

| 项 | 内容 |
|----|------|
| 修改 1 | `cors()` 改为 `cors({ origin: env.corsOrigins, methods: [...], credentials: false })`，默认仅放行 `http://localhost:3000`、`http://127.0.0.1:3000` |
| 修改 2 | 新增全局中间件：非 GET/HEAD/OPTIONS 请求校验 `Origin`，非白名单直接 403 |
| 修改 3 | `app.listen(port, env.host)`，`HOST` 默认 `127.0.0.1`；监听非回环地址时启动日志给出显式警告 |
| 修改 4 | `llmBaseUrl` / `embeddingBaseUrl` 校验：必须是合法 URL 且协议为 http/https；新增可选 `ALLOWED_MODEL_HOSTS` 域名白名单 |
| 理由 | 无鉴权 + `origin:'*'` + baseUrl 可写 ⇒ 任意网页可把模型地址改到攻击者服务器，真实 apiKey 随 `Authorization` 头外泄 |
| 验证 | 接口测试断言：非白名单来源的预检不返回 `Access-Control-Allow-Origin`；非白名单来源写请求 403；白名单来源 200；无 Origin 头正常放行；`javascript:` 与非法 URL 均 400 |

残余风险已在 `README.md` 的「安全边界」中显式文档化：`/api/config` 仍无身份认证、API Key 明文存储、`ALLOWED_MODEL_HOSTS` 为空时不限制域名。

## 五、未处理事项（含原因）

| 事项 | 原因与影响 | 建议 |
|------|-----------|------|
| 长任务移入 `worker_threads`（M1 的后半部分） | 文档解析（PDF/DOCX）是 CPU 密集且同步的，会短暂阻塞事件循环。本次已把最影响 SSE 的「逐条同步写」改为批量 + 事务（阻塞时间从 O(片段数) 降到 O(批次数)）；进一步改造需把解析与向量化整体搬入 worker，涉及消息协议与数据库句柄隔离，改动面较大 | 若后续出现大文档上传期间对话明显卡顿，再评估 worker 化 |
| 失败文档的「重试」接口（M3 的一部分） | 上传的原始文件不落盘（内存缓冲解析），失败后没有可重试的输入。凭空加一个只返回提示的接口没有意义 | 已改为：失败时清理干净 + 前端展示可读原因；如需重试，用户重新上传即可。已在 README 说明 |
| 引入 DOMPurify（P2-8 的后半部分） | 当前 `html: false` 已把模型输出中的原始 HTML 转义，markdown-it 默认也会拦截 `javascript:` 等协议，XSS 面已封闭。新增依赖的收益仅限于「将来若开启 html」这一假设场景，反而引入版本与包体积风险 | 保持现状，并在 `ChatView.vue` 与 README 中明确标注「若改为 html:true 必须同时接入净化库」 |
| `/api/config` 的身份认证 | 属产品形态选择（单用户本机 Demo 是否需要登录）。本次选择以「只监听回环 + CORS 白名单 + 写操作来源校验 + 文档化残余风险」应对 | 若要多机或多人使用，应加登录或本地令牌，并关闭 `HOST=0.0.0.0` 的裸暴露 |
| API Key 加密存储 | 加密密钥仍需在本机某处保存，对「本机可读文件」的攻击者没有实质增益，属安全剧场；真正的解法是接入系统密钥链或改为仅从环境变量注入 | 已在 README 标注明文存储这一事实 |
| 会话并发压测（M6 的验证） | 本次通过代码审查与类型检查覆盖，未构造「同会话并发两次 /send」的自动化压测用例 | 需要时可补：并发脚本断言历史顺序与内容一致性 |
| `docs/面试考点全解.md` | 与本次代码审查无关，未改动 | — |
